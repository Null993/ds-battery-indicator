# 工厂接口与固件后续分析

继续前一轮的官方库静态分析，目标仍是电池侧实时 V/I/W 和实际 SOC。本文所有 RVA 对应 `libFWupdater.dll` SHA-256 `3BC6DE1116A7EA29D0997F632613EDFE7C3100B62EFBF5BCA6F32F9FB4BC4569`，不适用于其他版本。

## 电量缓存来源闭环

新证据补足此前未追踪的缓存生产者：

1. RVA `D029..D050` 按 VID/PID 判定 DualSense / Edge，调用输入解析器 `F230`。
2. `F254..F258` 设置报告指针为输入缓冲区加传输偏移；USB 路径偏移为 0。`F3BB` 读此指针 `+0x35` 的字节，`F3BF` 写入中间结构 `+0x11`。因此 USB 对应含 ID 的 `wire[53]`。
3. `D0ED..D0F4` 把中间结构交给缓存函数 `6BA0`。`6C20` 设置缓存条目起点 `r13 = r15 + 0x170`；`6CA3..6CA8` 将中间结构 `+0x11` 复制到 `r15 + 0x1F8`。相对于缓存条目，这是 `0x1F8 - 0x170 = 0x88`。
4. `6F34` 将当前条目指针写入设备 `+0x168`；电量函数 `3DC3..3DCA` 从该指针的 `+0x88` 取值，再执行前文记录的低四位档位换算。

这条静态路径说明官方函数的该缓存来自普通输入报告，未在这里额外读取精确电池数据。它不证明控制器固件内从未测量电压、电流，也不排除未发现的其他接口。

## Feature 调用映射

新增离线脚本 `research/map_sony_calls.py` 输出 `call-map.json`、`linear-text.asm`。线性反汇编可能包含跳表等数据；只把经函数入口和上下文复核的调用作为证据，间接调用并未全部解析。

| 调用地址 RVA | 路径/参数证据 | 对电池测量的意义 |
|---|---|---|
| `1CF0/1D7B` | StartUpdate，`F4/F5`（另有设备分支使用 `F6/F7`） | 固件头传输/状态，无电池测量定义 |
| `1FF7/205D` | WriteUpdateImage，源缓冲区片段经复制进入 Feature 请求 | 已审阅段未发现主机解密步骤，不能从“官方能更新”推导主机持有明文固件 |
| `2268/22CB/245B` | Verify/Finalize 固件更新请求及状态 | 属于更新流程，未执行 |
| `2685/2A10/2A86/2C55/2F55` | Edge 配置读取、写入、删除、重置 | 不能把配置数据当电池遥测 |
| `34B9/3508` | 统计请求 `[80,70,01,...]`，读 `81` | 已确认是统计数据，未识别实时 V/I/W |
| `FDE1` | 调用内部组包函数 `10490`，设备 `18`、动作 `01`、两字节参数、总长度 5；有设备/版本和全局标志门槛 | 唯一识别出的该函数直接调用，语义尚未知，未发现 `Power=2` 调用，未发送 |

通用 GET wrapper `45B0` 经 `9D00` 调用 HidD_GetFeature；SET wrapper `4E40` 使用另一条通用发送路径。库还有直接的 HID 调用；已区分通用 wrapper 与真正的具体命令，不能把通用函数参数范围当作有效命令清单。

`10490` 在 `105D2..105D9` 组装 `[80,device,action]` 并复制剩余参数。其唯一识别的直接调用不能提供电源查询动作定义。尤其不能从其他设备的“动作 1 是读取”推断 Power/1 也只读。

## 新增公开源码查验

固定来源、commit 和哈希见 [追加来源清单](2026-09-30-additional-sources.json)。五个追加文件包含：

- dualshock-tools 网站当前 `ds5-controller.js`：电量仍读 payload[52]，状态 0/1 使用档位 ×10+5，状态 2 映射 100；工厂接口还有 NVS/校准/系统信息操作，没有已识别的电池 V/I 查询。
- dmitrymx/dualsense-diag 的 README、webhid.js、app.js：电池界面仍取同一低四位 ×10。其 charging 判断把状态 2 也计入充电，不能因为“专业诊断”描述就采用其语义或视为精密测量。
- nsfm 的 `scripts/dsp_explore.ts`：作者说明用于探索音频；脚本含未知动作/设备扫测，没有 Power 电压/电流定义。本项目只读源码，没有运行这些扫测。

补充 GitHub 查询（固件、诊断仓库，电压与固件解密 issue，CXD9006、DA9087 等）原始结果保存在 artifacts。空结果只表示本次检索没有命中；DA9087 代码搜索还返回了大量无关的颜色/数据字节匹配，未作为芯片资料。GitHub 操作按用户要求使用命令级代理。一次 Windows `rg` 文件通配符调用失败，改用目录 `-g` 完成检查。

## 固件标准容器验证

新增 `research/scan_firmware_containers.py`，对两份固件逐偏移检查标准容器魔数及 zlib 头。解压输出限制为 4 MiB，只接受完整、校验通过、输出至少 64 字节的 zlib 流。

gzip/bzip2 魔数候选亦作有界解码验证，未把仅仅出现的魔数当成有效容器。

| 固件 | zlib 头候选 | 合格完整 zlib 流 | 其他候选与验证 |
|---|---:|---:|---|
| 0520 | 865 | 0 | 偏移 866539 的 gzip 魔数候选解码失败：非法 header flags |
| 0630 | 893 | 0 | 偏移 887480 的 `BZh` 候选解码失败：Invalid data stream |

未命中 xz、LZ4 frame、zstd frame、ZIP 魔数。保存 `firmware/container-scan.json` 与两版前 256 字节的十六进制快照。0630 的 `0x80` 开始还存在 Wireless controller 2.10 和时间戳明文；这里只记录内容，没有将其误认为载入地址或解密密钥。

限制：没有覆盖无头压缩、字典、私有容器或具体密码算法。这不能证明加密，也不能证明解密不可能。目前仍没有可信的 MCU 指令集/载入映射和明文固件，因此未凭随机反汇编编造 Power action 表。一次 Python 命令行引号错误后改为 Format-Hex 保存头部，原文件未改变。

## 需求实现状态与继续条件

自动浮窗、功率开关/上下布局/共享中轴线、100% 完整绿色环已实现。精确 SOC 与电池侧实时功率读取仍未实现；标准报告没有提供所需精度，已审阅官方和第三方路径也未补足。

接回手柄后可以验证 21/22 的实际响应并采集充电中报告，继续比较候选字段。但要显示真实 W，还必须发现可验证的只读查询或固件解析字段，确认电池侧位置、单位和实时性；仅获得新的未知字节也不足以接入生产。若固件/接口未提供电池充电电流测量，纯软件无法制造此项观测，需设备侧额外测量能力。不能通过 USB 输入功率、额定值或档位变化推算后冒充实际电池充电功率。
