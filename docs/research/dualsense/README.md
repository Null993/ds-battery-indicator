# DualSense 电量与电池充电功率研究

研究日期：2026-09-30（Asia/Shanghai）。目标是读取更细的实际电量，以及**电池侧实际充电功率**，不是 USB 输入功率、额定功率或按使用时间估算的值。

本轮结论：已获取实机原始报告、22 个 Feature Report 能力条目和匹配当前版本的固件样本，发现可继续追踪的工厂测试命令通道；**尚未找到经过验证的精确 SOC、电池电压、电池充电电流或功率字段**。这些结论只覆盖本轮材料与实验，不等于证明未公开接口一定不存在。

## 已证实的实机结果

- 普通 DualSense：VID `0x054C`，PID `0x0CE6`，USB 游戏手柄接口；输入/输出/Feature 最大长度分别 64/48/64 字节。
- 10 秒样本：1,306 条有效 USB 输入报告，读取失败 0；含 ID 的 `wire[53]` 始终为 `0x2A`，按已知协议为“已充满、档位 10”。本轮没有充电中、放电和电量跨档样本。
- `GET_FEATURE 0x05`（校准）与 `0x20`（固件信息）成功，前后**数据**完全一致。JSON 时间戳不同，所以文件哈希不同不能解释成报告内容变化。
- 固件信息：编译时间 `Jul 4 2025 10:38:40`；`fwType=3`，`swSeries=0x000B`，`hardwareInfo=0x00001107`，主固件版本 `0x0110002A`，更新版本 `0x0630`。
- Sony 下载的 `FWUPDATE000B-0630.bin` 头部 PID、编译时间和更新版本与本机信息一致；这是版本匹配证据，不是整个运行中固件逐字节与下载文件一致的证明。

## 接口线索与当前解释

| 接口/字段 | 已有证据 | 判断与后续 |
|---|---|---|
| USB input `0x01`，wire[53] | Linux/SDL 与实机一致，低四位 10% 档位、高四位充电状态 | 继续做跨档记录；不能单靠这个字段恢复 1% 精度 |
| wire[49..52] | SDL 标为第二计时器；本轮中间差分多为 24000 | 时间戳线索较强，不作为电压/电流 |
| wire[56..63] | 各字节短期约 253–256 个不同值；几组常见 CRC32 假设均未匹配 | 仍未知；不能凭变化丰富就解释成高精度电量或功率 |
| Feature `0x05` / `0x20` | 公开校准/版本布局，实机前后不变 | 当前未见电池测量数据 |
| Feature `0x21` / `0x22` | 本机声明长度分别为 5/64 字节（含 ID） | 追加查询工具已构建，但运行时 USB 手柄未连接，尚未取得响应 |
| Feature `0x80` / `0x81` | dualsense-ts 描述为工厂测试请求/响应，枚举包含 `Power=2` | 具体“读取电压/电流” action 还没有可靠定义；下一轮优先找 action 表 |
| Feature `0x82` / `0x83` | ds5-calibration-tool 中用于开始/采样/提交校准及读状态 | 属于校准流程，未执行，不当成电量接口 |
| Feature `0xF4` / `0xF5` | dualsensectl 更新代码：固件传输/更新状态 | 离线读源码，未对设备发送更新命令 |

本机声明的 Feature ID（十六进制）：`05, 08, 09, 0A, 0B, 0C, 20, 21, 22, 80, 81, 82, 83, 84, 85, A0, E0, F0, F1, F2, F4, F5`。这些不是 22 个已知遥测接口。

dualsense-ts 的 `DspDevice.Power=2` 是一个有价值的第三方线索，仍需独立证据。该项目提供了读取序列号的具体 action（System/0x13），并没有在本轮检查的文件中提供读取电池电压/电流的 Power action。报告 ID `0x80` 是发送命令所用的 SET_FEATURE；不能把通道可用等同于任意 action 都是只读。

本机 Sony PlayStation Accessories 2.2.1.2 的静态分析进一步确认：`libFWupdater!GetBatteryLevel` 的 DualSense 分支仍使用低四位档位乘 10 加 5，最高档映射 100。其 `GetTelemetryDataDualSense` 对应的结构记录充电/连接次数与异常统计，没有瞬时电压或电流。找到工厂统计请求 `[80,70,01,...]`，但没有对手柄执行它；完整路径和限制见官方程序分析。

## 固件初步分析

两份 Type 000B 固件均为 950,272 字节，SHA-256 与公开档案一致：

| 版本 | 来源 | SHA-256 |
|---|---|---|
| `0x0630` | Sony 官方下载地址直连 | `B66528795683D214CA06FE4672D298DE75BF019BD5046442CBEC63FC02974F86` |
| `0x0520` | 官方地址 404 后使用固定 commit 的公开档案 | `79A20C4F58679CBF3876049E99254703014BBE8F368FD8BC601898A3F8BBB201` |

文件开头有明文版权、日期、版本等信息；PID 位于 `0x62`，更新版本位于 `0x78`（dualsensectl 源码与实测一致）。整体字节熵约 7.934 bit/byte；多数 16 KiB 块接近随机分布，少数块熵低。两版本同位置仅 33,491 字节相同，所有 16 KiB 块均有变化；没有找到 battery/voltage/current/power/charging 的连续 ASCII 文本。

高熵可以来自加密、压缩或其他编码，**目前没有识别具体算法，也未确认执行架构/载入地址**。不能据此宣称已经解密或定位充电程序；强行按 ARM 指令反汇编高熵数据会产生无效结论。本轮完成了固件来源、头部和结构统计，未得到电池测量逻辑。

## 下一轮实验的判定标准

1. 获取当前型号/固件对应的工厂 `Power` 设备 action 定义。优先读更多源码、公开逆向资料或官方应用的协议调用；只测试有证据表明属于查询的具体命令，不枚举未知写动作。
2. 采集“充电中、接近满电、满电”多个状态，尽量保持其他输入不动并记录真实开始/结束条件。本轮满电短样本不能检验候选数据与充电电流的关系。
3. 若找到疑似电压/电流，验证单位、比例、字节序、刷新率和测量位置。USB VBUS 电压或 USB 输入电流不能直接作为电池侧测量值。
4. 与独立电池侧测量或可靠厂商说明交叉验证后，才把 `P_battery = V_battery × I_charge` 接入应用。设备总输入功率包含手柄自身耗电和转换损耗，不能替代电池充电功率。
5. 精确 SOC 也需验证参考值和量化步进；电压推算 SOC 仍是估算，不能标为真实百分比。

## 本次浮窗修改

功率开关默认关闭；开启并保存后采用 160×80 双行布局，功率在百分比上方，与百分比共用中轴线。关闭后恢复 140×64。当前生产解析器的 `ChargingPowerWatts` 保持 null，界面显示“— W”，明确表示未知。

修复了单个圆弧在 360° 起终点重合导致满电环消失的问题；100% 使用两段半圆组成完整环。0% 不显示有色小点；充电时进度环仍与百分比一致，只让中心图标呼吸闪烁。已充满状态为完整绿色环。

已通过 56 项回归检查和两种布局的 PNG 视觉检查。测试中 2.37 W 只用于验证数值格式通路，是合成夹具，不能证明设备已提供功率。
